# SDD-фреймворк: проект набора скиллов

Oct 27, 2026 · @Andrei

## Цель и принципы

Плагин `sdd` из 8 скиллов для spec-driven разработки greenfield и brownfield проектов. Он даёт три вещи: компактный durable-контекст проекта, решения, принятые совместно с человеком, и спеки, которые исполняются через `/goal` с проверяемыми критериями приёмки.

- **Источник истины — md.** HTML генерируется из md скриптом без LLM и коммитится как представление для человека.
- **Один факт — одно место.** Остальные артефакты ссылаются на него, а не повторяют. У каждого файла есть бюджет строк.
- **Артефакты делятся по назначению и политике загрузки**, а не по разделам одного файла.
- **Решение фиксируется только после явного согласия человека.** ADR хранит и отвергнутые варианты, и условие пересмотра.
- **Изменение описывается дельтой к текущему состоянию** (ADDED / MODIFIED / REMOVED, модель [OpenSpec](https://openspec.dev)). При закрытии фичи дельта вливается в durable docs, иначе они расходятся с кодом.
- **MUST-правило по возможности исполняется проверкой**, а не текстом.
- **Критерий приёмки — команда с кодом возврата.** Оценщик `/goal` — маленькая модель, которая читает транскрипт; расплывчатый критерий она примет на слово ([docs](https://code.claude.com/docs/en/goal)).

## Слои артефактов и политика загрузки

Четыре назначения — четыре слоя. Агент всегда видит только слой 1 и нужные правила слоя 2; слои 3 и 4 читают скиллы по ссылкам.

| Слой | Файлы | Когда загружается | Бюджет |
| --- | --- | --- | --- |
| 1. Начальный контекст | `CLAUDE.md`, `docs/context.md` | Всегда (импорт в CLAUDE.md) | CLAUDE.md ≤40 строк, context.md ≤150 |
| 2. Правила генерации | `.claude/rules/*.md`, `docs/architecture.md` | Правила без `paths` — всегда; с `paths` — при работе с файлами по glob. architecture.md — скиллами spec, review | ≤60 строк на файл правил |
| 3. Ревью и подтверждение | `product.md`, `architecture.md`, `spec.md`, `docs/views/*.html` | Скиллами по запросу; человек читает HTML | spec.md ≤150 строк |
| 4. История | `decisions/*.md`, `specs/archive/`, идеи со статусом `dropped` | Только через `decisions/index.md`: скиллы idea, decide, spec, audit | ADR — один экран |

`decisions/index.md` — мост между слоями 1 и 4: одна строка на решение и раздел «Отвергнуто — не предлагать». Скиллы читают индекс, а полный ADR открывают только при совпадении темы.

Условная загрузка `.claude/rules/` по `paths` встречает баги в отдельных конфигурациях — после настройки проверьте через `/memory`, что загрузилось.

## Набор скиллов

Восемь скиллов. Исполнение фичи — встроенный `/goal`, отдельный скилл для него не нужен: `sdd:spec` выдаёт готовую строку команды.

| Скилл | Когда | Что делает | Пишет |
| --- | --- | --- | --- |
| `sdd:init` | Один раз на проект | **Greenfield:** интервью о продукте, границах, архитектуре верхнего уровня, стеке. **Brownfield:** субагенты сканируют код по модулям и строят as-is; выводы помечаются `inferred` и делятся на намеренное и «похоже на баг», затем подтверждаются с человеком | context, product, architecture, rules, первые ADR, `sdd.yaml` |
| `sdd:idea` | Появилось намерение | Быстрая фиксация без дизайна: проблема, результат, что не входит, вопросы. Проверяет дубли и раздел «Отвергнуто» | `ideas/<slug>.md` |
| `sdd:decide` | Архитектурный вопрос; вызывается и из spec, init | Формулирует вопрос, сверяется с индексом, предлагает 2–3 варианта с trade-offs. ADR пишется только после явного «да» | ADR + строка в index |
| `sdd:spec` | Идею берём в работу | Интерактивно, вопросами пачками: цель, scope, дельта к архитектуре, диаграмма изменяемой части, AC как команды, риски. Без кода | `specs/<slug>/spec.md`, `verify.sh`, строка `/goal` |
| `sdd:view` | После spec, close; вручную | Детерминированный рендер md в HTML: продукт, C4, sequence, дерево решений, страница ревью спеки | `docs/views/**` |
| `sdd:review` | После `/goal` | Субагент в чистом контексте сверяет diff со спекой и MUST-правилами, проверяет вывод `verify.sh`, ищет незаявленные изменения архитектуры | Отчёт в `specs/<slug>/review.md` |
| `sdd:close` | Перед мержем, в той же ветке | Вливает дельту в architecture, context, rules; присваивает номера ADR; переводит статусы; переносит спеку в archive; вызывает view | durable docs, archive |
| `sdd:audit` | Периодически | Расхождения docs и кода, превышение бюджетов, противоречия правил, «сироты» в index | Отчёт; правки — через decide |

## Жизненный цикл фичи

У фичи два гейта: человек принимает спеку, CI пропускает мерж. Между ними `/goal` работает без участия человека.

Человек принимает спеку по HTML-странице из `sdd:view`. Отказ возвращает работу в `sdd:spec`, замечания ревью и красный CI — в `/goal`. `sdd:init` запускается один раз до первой идеи.

## Файловая структура

Всё, что относится к фреймворку, лежит в `docs/` и `.claude/rules/`; `sdd.yaml` — единственная точка, где скиллы узнают стек и команды. Идея и спека живут под одним slug от начала до архива.

```
CLAUDE.md                     ≤40 строк: команды + @docs/context.md
sdd.yaml                      стек, команды build/verify, бюджеты, пути
.gitattributes                docs/views/** linguist-generated=true -diff
.claude/rules/                [2] правила генерации кода
  00-stack.md                 без paths → всегда: стек, версии, запреты
  <area>.md                   paths: <glob> → MUST/SHOULD области
docs/
  context.md                  [1] продукт в 3 строках, карта модулей, инварианты
  product.md                  [3] проблема, пользователи, сценарии, non-goals
  architecture.md             [2][3] C4, модули, границы, потоки, интеграции
  decisions/
    index.md                  [1→4] строка на ADR + «Отвергнуто — не предлагать»
    0007-<slug>.md            [4] номер присваивает sdd:close
  ideas/
    <slug>.md                 status: new | specced | dropped
  specs/
    <slug>/
      spec.md                 [3] вход для /goal
      verify.sh               AC как команды
      review.md               отчёт sdd:review
    archive/2026-10/<slug>/   [4]
  views/                      [3] сгенерированный HTML, коммитится
    index.html                точка входа со ссылками на всё
    product.html  architecture.html  decisions.html
    specs/<slug>.html
```

Цифры в скобках — слой из раздела «Слои артефактов». Номера ADR раздаются при закрытии, а не при создании: так параллельные ветки команды не конфликтуют по номерам.

## Форматы ключевых артефактов

Каждый артефакт — frontmatter для машин и короткие разделы для людей. Пустой раздел удаляется, а не заполняется «N/A».

| Артефакт | Frontmatter | Разделы |
| --- | --- | --- |
| `context.md` | `updated` | Продукт в 3 строках · Карта модулей → пути · Инварианты (≤10) · Команды · Где искать дальше (ссылки) |
| ADR | `status: proposed / accepted / superseded / rejected`, `date`, `supersedes`, `parent`, `tags` | Контекст · Варианты (по строке + почему нет) · Решение · Последствия · **Пересмотреть, если** |
| `index.md` | — | Таблица: id · статус · решение в одну строку · заменяет. Раздел «Отвергнуто»: что · почему · ADR |
| Идея | `status`, `date` | Проблема · Желаемый результат · Не входит · Открытые вопросы. ≤15 строк |
| Спека | `status: draft / approved / in-progress / done`, `idea`, `adrs` | Цель · Scope / Non-scope · Дельта архитектуры · Диаграмма изменяемой части · Решения (ссылки на ADR) · AC · Риски · Goal |

Поле `parent` в ADR строит дерево решений: `sdd:view` рисует его из этих полей, отдельного файла дерева нет. Раздел «Пересмотреть, если» — главный механизм против хождения по кругу: решение можно поднять снова только при наступлении названного условия.

AC в спеке — таблица `id · критерий · команда`. Поведенческие тесты содержат id критерия в имени (`AC3_offlineQueueSurvivesRestart`), чтобы review видел трассировку. Раздел Goal — готовая строка:

```
/goal Спека docs/specs/offline-mode/spec.md выполнена: docs/specs/offline-mode/verify.sh завершился с кодом 0, полный вывод показан в транскрипте
```

В `verify.sh` — только команды стека из `sdd.yaml` (`./gradlew test --tests …`, `cargo test …`, `flutter test …`, `swift test …`) и проверки AC.

## HTML-представления: генерация и хранение

HTML генерируется и коммитится: последняя версия всегда лежит в `docs/views/`, прошлые — в истории git. Из md его собирает скрипт внутри `sdd:view`, без LLM, поэтому результат детерминирован и ничего не стоит в токенах.

- **Диаграммы** — mermaid в md, при сборке пререндерятся в SVG через mermaid-cli. HTML открывается офлайн и не зависит от CDN.
- **C4** — mermaid `flowchart` с подграфами в стиле C4. Нативный синтаксис C4 в mermaid пока экспериментальный; если команда уже использует Structurizr или PlantUML C4, генератор можно переключить.
- **Шум в ревью** — `.gitattributes` помечает `docs/views/**` как generated и отключает diff, поэтому PR показывает только изменения md.
- **Свежесть** — CI перегенерирует views и падает при расхождении (`git diff --exit-code docs/views`). Устаревший HTML в main невозможен.
- **Навигация** — `index.html` ссылается на продукт, архитектуру, дерево решений и все спеки, включая архивные.

Страница спеки собирает в одном месте то, что нужно для «ок» человека: цель, дельту архитектуры с подсветкой, диаграмму, AC и ссылки на ADR. После `sdd:review` к ней добавляется отчёт ревью.

## Enforcement правил по стекам

Для всех шести стеков есть инструменты, которые проверяют архитектурные границы как тесты или линт. MUST-правило в `.claude/rules/` ссылается на свою проверку строкой `Проверяется: <тест/правило>`. Правило без проверки помечается `(manual)` и попадает в чек-лист `sdd:review`.

| Стек | Границы модулей | Статика и стиль |
| --- | --- | --- |
| Java / Spring | ArchUnit (JUnit); Spring Modulith `ApplicationModules.verify()` | Checkstyle или Spotless, Error Prone |
| Kotlin / Quarkus | Konsist (тесты), ArchUnit по байткоду | detekt, ktlint |
| TypeScript | dependency-cruiser или eslint-plugin-boundaries | eslint, `tsc --noEmit` |
| Rust | Crates в workspace: компилятор не пропустит необъявленную зависимость; `pub(crate)` | `cargo clippy -D warnings`, `cargo fmt --check`, cargo-deny |
| Dart / Flutter | [import\_rules](https://pub.dev/documentation/import_rules/latest/) или [dart\_boundaries](https://pub.dev/packages/dart_boundaries) (custom\_lint) | `dart analyze`, `dart format --set-exit-if-changed` |
| Swift | Таргеты SPM; [Harmonize](https://github.com/perrystreetsoftware/Harmonize/wiki) — правила как unit-тесты | SwiftLint |

Плагин хранит шаблоны правил и проверок по стекам (`templates/<stack>/`). `sdd:init` берёт стек из кода или интервью, записывает его в `sdd.yaml` и раскладывает шаблоны. Для монорепо с несколькими стеками `sdd.yaml` задаёт стек на каждый путь.

## CI и PR при наличии сборки

Все проверки действительно живут в сборке. CI — это не второй набор проверок, а тонкая обёртка: она запускает тот же `verify`, но там, где его нельзя пропустить или ослабить.

| Вопрос | Только локальная сборка | Сборка + CI |
| --- | --- | --- |
| Кто гарантирует запуск | Агент или человек; можно забыть, `--no-verify`, `-x test` | Каждый push и PR, без исключений |
| Может ли агент ослабить проверку | Да: поправить тест, `verify.sh` или конфиг сборки, чтобы «позеленеть» | Изменения правил и CI-конфига под CODEOWNERS требуют одобрения человека |
| Окружение | Локальные кеши, переменные, версии инструментов | Чистое и воспроизводимое |
| Параллельные ветки | Каждая зелёная отдельно, вместе красные | Проверяется результат слияния (rebase или merge queue) |
| Доказательство | Слова агента в транскрипте | Статус, привязанный к коммиту |

Для агентного процесса решает вторая строка. Агент оптимизирует под «зелёный», а оценщик `/goal` верит транскрипту, поэтому гейт должен стоять вне досягаемости агента.

PR в небольшой команде — единица одобрения: в нём фиксируется «ок» человека, лежат ссылки на спеку и отчёт ревью, и он даёт место, где CI блокирует мерж. Построчно diff читать не нужно: ревьюер смотрит HTML-страницу спеки и отчёт `sdd:review`.

Минимальная настройка:

1. CI-джоба вызывает ту же команду, что и локально: `verify` из `sdd.yaml` + `sdd check` (views свежие, статус спеки `done`, index согласован).
2. Защита `main`: мерж только через PR с зелёным CI и одним одобрением; squash merge.
3. CODEOWNERS на `.claude/rules/`, `docs/specs/*/verify.sh`, CI-конфиг и шаблоны проверок.

Без CI можно жить в одиночном прототипе. В команде с агентами это самая дешёвая страховка из возможных.

## Порядок реализации и открытые вопросы

Начинать с форматов: это контракт, на который опираются все скиллы. Brownfield-режим `init` лучше делать раньше greenfield, потому что он сразу проверит форматы на реальном коде.

1. Шаблоны артефактов (раздел «Форматы») и схема `sdd.yaml`.
2. `sdd:init`: сначала brownfield, затем greenfield.
3. `sdd:decide`.
4. `sdd:idea` и `sdd:spec`.
5. `sdd:view`: генератор md → HTML с пререндером mermaid.
6. `sdd:review` и `sdd:close`.
7. CI-шаблоны по стекам, `sdd check`, `sdd:audit`.

Открытые вопросы:

- [ ] Одна спека = одна ветка = один PR? Предлагаю да.
- [ ] Где живёт плагин: отдельный репозиторий и установка через marketplace команды?
- [ ] Язык артефактов. Кириллица обычно расходует больше токенов, чем английский, на тот же смысл; вариант — слой 1 и правила на английском, product и спеки на русском.
- [ ] Формат C4: mermaid или Structurizr / PlantUML?
